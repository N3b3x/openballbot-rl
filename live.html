This page runs the real controller. A neural network trained with PPO reads the robot's state 100 times a second and sets three wheel torques; MuJoCo, compiled to WebAssembly, simulates the physics. Set a velocity command, shove the robot, and watch it keep its balance on the ball. Everything here is simulation; no hardware was involved.

What the network does

Eight signals in, three torques out

The policy is a small multilayer perceptron: the actor has 22 inputs (the eight signals below), two layers of 256 tanh units and 3 outputs, about 72,000 weights (144,391 parameters including the value network that is only used in training). It has no camera and no memory beyond the last action and one integral term: it balances from the robot's own motion alone.

What it sees (live)

The five rows marked standardised are shifted and scaled with the running mean and variance recorded during training, then clipped to ±10; cmd, heading and vint are fed raw. Together they make 22 numbers.

What it outputs (live)

Each output in [−1, 1] is multiplied by 30 and applied as the torque in N m on one omniwheel motor (with the sign convention of the model). Five physics steps of 2 ms are simulated per decision, so the policy acts at 100 Hz.

An honest curiosity. The input called motor_state is meant to be the three wheel speeds. Reading the environment code (ballbot_gym/envs/ballbot_env.py) shows it indexes the velocity vector by joint number instead of degree-of-freedom address, so what the policy actually receives is [base vy, base vz, base roll rate] / 30 (entries 1 to 3 of the velocity vector, which belong to the base's free joint). The policy was trained on exactly that signal, so this page reproduces it, because faithful behaviour matters more than the label. So the row labelled motor_state in the table above is not a wheel speed.

Other checks

What this does and does not show. The agreement is measured on noise-free runs from a clean start. The policy was trained with domain randomisation (random masses, friction, torque scale, one-step latency, sensor noise and random pushes); this page runs the nominal model with no noise and no hidden pushes, so it shows what the policy does in the idealised case. Contact-rich chaotic dynamics eventually amplify tiny numerical differences, so longer runs than 8 s (or other commands) may drift further than the table shows; we only report what we measured. The floor is flat: the study's rough-terrain and book-climbing experiments are not reproduced here.
Why this was not obvious

Reproducing the omniwheel contact fix in JavaScript

The robot drives the ball with three omniwheels. Each wheel is modelled as a capsule that rolls freely along its own axis (friction 0.001) and grips across it (friction 1.0). Stock MuJoCo picks the first contact tangent arbitrarily, so that anisotropy points the wrong way. The study's Python environment therefore runs its own stepper that rewrites every ball-wheel contact frame so the first tangent follows the capsule axis.

How the browser does the same

  1. The official @mujoco/mujoco 3.13.0 build exposes the individual pipeline stages, so the step is split as in Python: kinematics, collision, rewrite frames, constraints, forces, then mj_implicit.
  2. data.contact is returned by copy, so writing to it has no effect. The frames are instead rewritten in place inside the live WebAssembly memory (data.arena), whose struct layout the page calibrates and verifies against data.contact before using it.
  3. Switch the fix off with the checkbox above and the same code falls over almost immediately, matching what the Python environment does without the fix (it also falls at control step 25 in the reference run).

Limits of this approach

  • It relies on the arena layout of MuJoCo 3.13.0, hence the pinned version and the start-up self-check. A different build could change the layout; the badge at the top turns amber if the check fails.
  • Single-threaded WebAssembly in your browser tab; speed depends on your device.
  • The model file is a snapshot of ballbot_gym/models/ballbot.xml with a down-scaled ball texture (visual only).
