From simulation to ROS 2

The controller was exported into a ROS 2 package and checked against the simulator, tick by tick. It has never run on a robot. There is no robot yet.

Simulation only, no hardware

You will be able to

  • name the layers of the package;
  • explain why a ballbot's safety logic latches faults instead of switching off;
  • say what a parity test proves, and what it does not.

10.1Three layers

Pure-Python coreEvery piece of control logic: estimator, motion layer, observation builder, actor, LQR, authority, safety. No ROS imports, enforced by a test.
Two thin ROS 2 nodescontroller_node reads /cmd_vel, /imu and /joint_states and writes /wheel_torque_cmd. estimator_node publishes /odom and the TF for Nav2.
The bundleThe trained network plus one JSON file with every setting. The node has no hard-coded numbers.
What is in the bundle

One folder (config/bundle/g39_goalcentre_s0/) with actor.onnx, actor.ts (TorchScript), actor_weights.npz (plain numpy) and bundle.json. Each actor file is about 2.6 MB. The JSON carries the control rate (100 Hz, torque held for 10 ms), the observation layout with units and clips, history length and order, the normalisation, the rule that combines LQR and network, the authority and motion-layer parameters, the LQR weights and per-design gains, the design table, the estimator calibration, the goal point (the true ball centre for g39) and the source run with its training arguments.

10.2Safety: a ballbot cannot just turn off

For most robots, "off" is safe. An unpowered ballbot falls. So the supervisor has three states, and a fault latches.

Try it

Enable the robot at 1 degree. Raise the tilt to 25 degrees: what happens? Then to 31. Then lower it back to 1 and press Enable: does it re-engage?

Show the answer

At 25 degrees it keeps going (the cutoff is 30). At 31 it latches FAULT and stays there even when the tilt returns to 1: the fault has to be cleared deliberately and the robot enabled again. Automatic re-engaging could spin the wheels against a fallen body.

10.3Parity: is the port the same controller?

The control logic exists twice: in the GPU simulator for training, and in the portable core. If they differ, the network sees inputs it never trained on.

So a recorded simulator run is replayed through the core and every intermediate signal is compared. The worst wheel torque difference was 1.3e-3 N m. The exported actors match the original network to below 1e-6.

10.4What was not verified

Parity shows the code is the simulator's code. It does not show that a robot behaves.

CheckedCore against simulator, tick by tick. Exported network against the original. Safety logic. A closed-loop run on CPU MuJoCo.
No ROS build or runROS 2 was not installed on the development machine. Nodes ran only against stand-in message classes.
No hardwareMotor signs, encoder directions, IMU mounting, torque mapping, driver latency, noise and timing are all unverified.
Not real-timePython and its ROS 2 executor are not real-time. The README lists three routes.
The remaining caveats
  • The state comes from an estimator, not from the simulator. The base angular velocity the policy saw in training was 2 ms older than a gyro sample would be (a median change of 1.8e-3 in the action), and some velocities are reconstructed from the ball-centre velocity (0.3 m/s at the 99th percentile during impacts).
  • Real-time routes. An isolated core with a real-time kernel, a ros2_control C++ plugin with the Python core as the test oracle, or the whole balance loop on a microcontroller.
  • Open issues. The adaptive-authority dead band in the simulator reads the ball body-origin speed, which the core replaces by the centre speed (S122 retrains with the centre speed). The "motor" observation entries are base velocities divided by torque, a training artefact that the core reproduces.
  • Parity numbers. 13,299 ticks, 33 worlds, all 11 designs: 1.3e-3 N m for g39 (1.5e-3 for the earlier g34). TorchScript matches exactly, numpy float64 to 2.4e-7.
Check yourself

Why does the parity test feed the core the simulator's exact state instead of the estimator's output?

Why

Testing the two questions separately makes failures interpretable. If the parity test also ran the estimator and failed, you would not know whether the logic or the estimate was wrong. The estimator is checked against its own reference (the study's odometry.py) and the closed-loop run on CPU MuJoCo puts the two together; on hardware the second question would be the main one, and the tests cannot answer it.

SummaryKey takeaways

  • The package is a pure-Python core, two thin ROS 2 nodes and an exported bundle. The core runs without ROS.
  • One bundle.json plus the actor files describes the whole controller.
  • Safety is HOLD, ACTIVE and FAULT. A fault latches; a command timeout holds position.
  • Parity: the port matches the simulator to float32 rounding (1.3e-3 N m worst torque difference). It does not show that a robot works.
  • No ROS build, no hardware: stated limits, not footnotes.
