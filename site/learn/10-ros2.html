From simulation to ROS 2

A trained controller is only useful if it can leave the simulator. This lesson follows it into a ROS 2 package: the pieces, the safety logic, how the port is checked against the simulator, and what is still unknown because there is no robot.

Simulation only, no hardware

You will be able to

  • name the layers of the package and where each lesson's idea lives in it;
  • explain why a ballbot's safety logic latches faults instead of disabling;
  • say what a parity test proves, and what it does not.

10.1From a simulator checkpoint to a ROS 2 controller

Everything so far lives in a simulator on a GPU. The last step is to make the controller something a robot could run: a software package that reads an IMU and three wheel encoders, runs the stack of lessons 3 to 7, and writes three motor torques every 10 ms, with a Nav2 navigation stack above it. The package is ros2/ballbot_control. It is built to be tested without ROS, and it has never run on a robot or even under a real ROS installation: there is no physical robot yet (the section "What was not verified" below is part of the lesson).

The design has three layers, from least to most ROS:

  • A pure-Python core (numpy only, no ROS imports, enforced by a test) holding every piece of control logic: estimator, motion layer, observation builder, actor, LQR, authority and safety.
  • Two thin ROS 2 nodes: controller_node (100 Hz, subscribes to /cmd_vel, /imu and /joint_states, publishes /wheel_torque_cmd and diagnostics) and estimator_node (publishes /odom and the TF for Nav2).
  • An exported bundle: the trained policy and everything needed to run it, written by export_policy.py from a checkpoint.

10.2The exported policy

A checkpoint is exported into one folder (config/bundle/g39_goalcentre_s0/) with four files: actor.onnx, actor.ts (TorchScript), actor_weights.npz (plain numpy) and bundle.json. Each actor file is about 2.6 MB. The JSON file carries everything that is not weights: the control rate (100 Hz, torque held for 10 ms), the observation layout with units and clips, history length and order, the normalisation, the rule that combines LQR and network, the authority and motion-layer parameters, the LQR weights and per-design gains, the design table with the 6-number design vectors, the estimator calibration, the goal point (the true ball centre for g39) and the source run with its training arguments. One file describes the whole controller, so the node needs no hard-coded numbers; a controller trained later with different settings runs by loading its bundle.

10.3Safety, because a ballbot cannot just turn off

For most robots "disable" is the safe state. For a ballbot it is the opposite: unpowered, it falls. The supervisor therefore has three states. HOLD (startup, or after disable) applies zero torque and expects the robot to be held or on a stand. ACTIVE is balancing; it is entered only on an enable request while the body is within 3 degrees of upright and the sensor data is fresh, and it resets the controller as a training episode would start. FAULT latches on a tilt above 30 degrees, a non-finite value, or sensor data older than 50 ms, with zero torque until the fault is cleared and the robot is enabled again. A command that stops arriving (0.5 s) does not disable anything: the robot stops and holds position, because an upright ballbot must keep balancing.

Try it

Enable the robot at 1 degree. Raise the tilt to 25 degrees: what happens? Then to 31. Then lower it back to 1 and press Enable: does it re-engage?

Show the answer

At 25 degrees it keeps going (the cutoff is 30). At 31 it latches FAULT and stays there even when the tilt returns to 1: the fault has to be cleared deliberately and the robot enabled again. The latch is the point. After a fault the state of the robot is unknown, and automatic re-engaging could spin the wheels against a fallen body.

10.4Parity: does the port do what the simulator did?

The control logic was written twice, once in the GPU simulator for training and once in the portable core. If they differ even slightly, the trained network sees inputs it never saw. So the project replays a recorded simulator rollout through the core and compares every intermediate: the shaped command, the 25-number observation, the 255-number actor input, the network action, the LQR action, the authority and the final wheel torque. For the recommended controller the worst-case torque difference over 13,299 ticks, 33 worlds and all 11 designs was 1.3e-3 N m (1.5e-3 for the earlier g34). The exported actors match the original network to below 1e-6 (TorchScript exactly, numpy float64 2.4e-7).

10.5What was not verified

A parity test shows that the code is the simulator's code; it does not show that the robot behaves. These are stated plainly in the package README, and they are the reason this lesson says "could", not "does":

  • No ROS build or run. ROS 2 was not installed on the development machine. The nodes were only exercised against stand-in message classes, which checks wiring, not executors, QoS, TF, Nav2 integration or timing.
  • No hardware. Motor sign conventions, encoder directions, IMU mounting, torque mapping, driver latency, sensor noise and compute timing are all unverified.
  • The state comes from an estimator, not from the simulator. Two approximate mappings: the base angular velocity the policy saw in training was 2 ms older than a gyro sample would be (a median change of 1.8e-3 in the action), and some velocities are reconstructed from the ball-centre velocity (0.3 m/s at the 99th percentile during impacts).
  • Real-time. Python and the ROS 2 Python executor are not real-time; the README lists three routes (an isolated core with a real-time kernel, a ros2_control C++ plugin with the Python core as the test oracle, or the whole balance loop on a microcontroller).
  • Open issues. The adaptive-authority dead band in the simulator reads the ball body-origin speed, which the core replaces by the centre speed; retraining with the dead band on the centre velocity would remove that. The "motor" observation entries are base velocities divided by torque, a training artefact that the core reproduces and a future retraining should replace with real wheel rates.
Check yourself

Why does the parity test feed the core the simulator's exact state instead of the estimator's output?

Why

Testing the two questions separately makes failures interpretable. If the parity test also ran the estimator and failed, you would not know whether the logic or the estimate was wrong. The estimator is checked against its own reference (the study's odometry.py) and the closed-loop run on CPU MuJoCo puts the two together; on hardware the second question would be the main one, and the tests cannot answer it.

SummaryKey takeaways

  • The package splits into a pure-Python core, two thin ROS 2 nodes and an exported bundle; the core runs without ROS.
  • One bundle.json plus the actor files describes the whole controller, including the goal point, motion layer and authority.
  • Safety is HOLD, ACTIVE and FAULT; a fault latches and a command timeout holds position rather than disabling.
  • Parity shows the port matches the simulator to float32 rounding (1.3e-3 N m worst torque difference); it does not show that a robot works.
  • No ROS build, no hardware, estimator mapping approximate: stated limits, not footnotes.
