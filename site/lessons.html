Lessons

Lessons from building this

Eight things that went wrong in a way worth remembering. Each one changed a result, cost a re-run, and left behind a rule and a line of code that enforces it. Ordinary bugs (timeouts, misread listings) are not here.

Simulation only, no hardwareDevelopment lessons, not a bug list

Sources: docs/research/tracking_study_log.md, cited by entry number, and the files named under each lesson. Terms link to the glossary.

The eight rules

  1. Recompute every derived field when you batch a model field, and test far from the origin. Lesson 1
  2. Every setting that changes a result goes into the file name and into the file. Lesson 2
  3. Check that every world is exposed to the feature you are measuring before you read the rate. Lesson 3
  4. Record where failures happen, not only that they happened. Lesson 4
  5. A conditioning vector's reference frame is part of the model; fix it once, and verify it on held-out inputs. Lesson 5
  6. Place mechanisms at the loaded pose: settle under gravity first. Lesson 6
  7. Aim the sensor where the planner is going, not where the robot is going. Lesson 7
  8. Log a non-finite state separately from a fall, treat extreme friction ratios as a float32 hazard, and put a long stationary test in every protocol. Lesson 8
Cited to S65, S69, S70, S78, S79, S85-R, S86, S87, S90, S92 and S98 of the study log.
Lesson 1
Physics engine

Engine invariants: a stale derived field

Randomising a body's mass without recomputing the engine's cached subtree mass corrupted the physics in proportion to the robot's distance from the world origin.

What happened

The GPU engine finds each body subtree's centre of mass by dividing mass-weighted positions by a stored field, body_subtreemass, and uses that point as the reference of the dynamics. Domain randomisation scaled body_mass of the ball and base per world but never updated the stored subtree mass, so the reference point was wrong by a fraction of the robot's distance from the origin; training and evaluation tiles lie up to 12 m out (S69).

The error is zero at nominal mass, which is why every unrandomised run looked fine and why a mass ablation "found" that mass randomisation was the main cause of falls. A second copy of the same fault lived in the evaluation path: set_design wrote each design's nominal subtree mass back over the corrected value (S70).

What it cost

Every domain-randomised result before S69, training or evaluation, was superseded: all goal-task and tile-velocity evaluations from S37 to S68, every policy trained up to that point (g2 to g11), and the conclusions "wide randomisation does not help" (S67) and "mass is the driver" (S68), which were artefacts. Three training runs were stopped and the whole recipe chain was retrained as g12 on the corrected engine (S69, S70, S71).

Not lost: anything with randomisation off, such as the flat-world tracking benchmark and the LQR calibration.

The rule and the guard

Rule. When you batch or randomise a model field, recompute every field the engine derives from it, and test far from the origin, where position-dependent errors show.

Guard. experiments/warp_ppo/train_dev.py: _subtree() recomputes the subtree masses from the per-world masses at every reset and again inside set_design; experiments/warp_ppo/lqr_gpu.py does the same for the LQR-only runs. The corrected ablation (S70) shows no single randomisation term dominating, which is the sanity check to repeat after any engine change.

Lesson 2
Bookkeeping

File names carry settings

Evaluation files were silently overwritten until every setting that changes a result went into the file name and into the JSON itself.

What happened

In the S53 era the evaluation script wrote one JSON per run and task. It did not record the push scale, the DR scale, the flat-world flag or the no-exit flag, and a later evaluation with different settings reused the same file name. The goal-task files of one run ended up holding the DR scale 2.5 results after a later chain ran over them (S65).

A site and paper cross-check (docs/research/site_crosscheck.md) found the mismatch when the files no longer matched the printed numbers in the log. A depth-sensor battery was later overwritten in the same way by an accidental second run (S78).

What it cost

The cross-check had to re-derive which stored file belonged to which experiment, and corrected the world counts of four flat-benchmark entries (64 worlds, not 32), one ramp-up value and three wording claims about accuracy and speed (S65). The S78 depth battery survives only as the second run's file; the two runs differed by up to 0.02 in goal success, which became the study's direct measure of evaluation noise.

No conclusion changed, but no stored file from before S65 can be trusted without the log entry that printed it.

The rule and the guard

Rule. Every setting that changes a result goes into the file name and is stored inside the file; a result file that can be overwritten by a different experiment is not a record.

Guard. experiments/warp_ppo/eval_tiles2.py appends _ps, _drs, _flat, _noexit, _off- and the tile seed _ts to every file name and stores an env_settings block in the JSON; experiments/warp_ppo/eval_battery.py runs the standard battery with every setting explicit and writes one battery.json per run. The site reads a frozen snapshot, site/data/eval_snapshot/.

Lesson 3
Evaluation design

Exposure artefacts

Eight-second episodes made slow robots look safe on obstacles because, at low speed, many of them never reached the obstacle.

What happened

A speed sweep on the terrain tiles showed step-up falls dropping from 0.62 at 0.3 m/s to 0.16 at 0.1 m/s, and bump falls from 0.74 to 0.16 (S86). The conclusion was that an obstacle-aware speed layer could remove most terrain falls.

Terrain features start 0.6 m or more from the tile centre. In an 8 s episode at 0.1 m/s the robot travels about 0.8 m, so many worlds ended before the robot touched the feature and were counted as survivors. With 20 s episodes the low-speed advantage largely vanished, step-up falls reading 0.64 at every speed (S87); the part of that reading that was a solver blow-up is the subject of lesson 8, and the exposure correction itself stands. This is the exposure artefact.

What it cost

S86 was withdrawn. The speed-governor idea it motivated was still built and tested, as a privileged slow-down near discontinuities, and moved falls only from 0.39 to 0.37 (S87), so it was dropped. The corrected analysis then had to be done by feature size instead of speed, which produced the traction limit (S87, S88) and redirected the perception work from climbing to routing (S89). The size result stands; the "speed does not matter" part of S87 was later superseded on the corrected contact model (S100, see lesson 8).

The second instance. Re-tested on the corrected contact model, the speed layer looked like it halved obstacle falls, but those episodes were 15 s long and slowed robots covered only 0.96 to 1.07 m against features from 0.6 m out. With 40 s episodes the falls are 0.38 with no layer, 0.33 with the perfect-map layer and 0.35 with the ToF layer: the layer is worth 0.03 to 0.05, mostly on stairs (S103). The halving was withdrawn, along with the site claims built on it.

The third instance. A zigzag test (60 degree command switches every 2 s for 15 s) cost 0.28 to 0.33 of robots for every motion-layer variant and was read as a turning weakness. The test started each robot on a flat tile, but the zigzag carried it about 2 m onto neighbouring terrain tiles; on a fully flat map the same test falls 0.051, while a curve test that stays on its tile falls 0.03 to 0.05 (S113 zigzag addendum). It was measuring terrain exposure, not turning.

The rule and the guard

Rule. A slowed robot must be given the time to meet the obstacle; check exposure every time an intervention changes speed. Episode length times the slowest speed must exceed the distance to the feature, and the denominator must count only exposed worlds.

Guard. experiments/warp_ppo/eval_governor.py runs with no episode truncation inside the evaluation (max_steps raised) and a --steps length chosen per protocol; every terrain result since S87 uses 20 s episodes. experiments/warp_ppo/tiles.py records each feature's drawn severity (RANGE), so results are split by size, not by speed.

Lesson 4
Evaluation design

Finite maps

Robots driving off the edge of the height field were counted as falls, which inflated every flat-ground fall rate and made falls appear to rise with speed.

What happened

The flat benchmark placed its 64 worlds on the tile positions of the normal protocol, which include the border tiles of the 24 m height field: tile centres at 10.5 m, 1.5 m from the edge. With tile-exit truncation off, a robot driving outward left the height field and the termination check called it a fall (S92).

A new per-fall position record showed that at 0.9 m/s for 8 s, 97 percent of the recorded flat falls were within 0.6 m of the border (0.25 recorded, about 0.01 real), and at 0.3 m/s for 20 s over 11 designs, 74 to 76 percent (0.33 recorded, about 0.08 real). This is the map-edge artefact.

What it cost

The "flat falls" column of every battery since S59 was superseded, and the 8 to 15 percent flat base rate quoted in S87 and S89 with it. The flat rows of every battery were re-run on interior tiles. Tracking error and achieved speed were computed over surviving worlds and were unaffected (S92).

The corrected base rate then appeared design specific, with the extreme-ball designs carrying nearly all flat falls (S92 addendum, S93); the standing part of that picture was itself an artefact, see lesson 8.

The rule and the guard

Rule. Record where failures happen, not only that they happened; a failure at the boundary of the simulated world is a property of the world, not of the controller.

Guard. experiments/warp_ppo/eval_tiles2.py stores the fall position of every world and a fall_at_map_edge fraction (fell within 0.6 m of the border); experiments/warp_ppo/eval_battery.py --flat-only re-runs the flat benchmark on interior tiles at least 7.5 m from the border and keeps falls_at_map_edge in battery.json, so a non-zero value is visible in the file.

Lesson 5
Policy inputs

Reference frames for conditioning vectors

Held-out robot designs were described to the policy relative to the wrong reference design, so the generalisation test fed the policy a design vector it had never seen in training.

What happened

Design-conditioned policies receive a 6-number design vector computed relative to a reference design. In training the nominal design is loaded first and is the reference. The held-out evaluation loaded only the two unseen designs, so the vector was computed relative to the first of them: the 1.5x robot was presented as nominal-sized, and the low-torque design was described relative to the 1.5x robot (S87, S85 suspended).

The LQR part of the controllers always used the correct per-design gains, so only the learned residual saw the wrong input.

What it cost

S85 and the held-out design addendum of S83 were suspended and could not be used until the re-run was logged. The re-run (S85-R) reproduced the conclusions on correct inputs: LQR-based controllers keep 0.61 to 0.71 on the unseen larger robot, pure learning collapses to 0.09 to 0.15, and the tenth-torque design is motor limited for every controller. The cost was a re-evaluation and a period in which the study's main generalisation claim had to be marked unusable.

The rule and the guard

Rule. A conditioning vector's reference frame is part of the trained model; define it once, independent of what is loaded at evaluation, and verify held-out inputs against a training-time vector before reading any generalisation number.

Guard. experiments/warp_ppo/train_dev.py: the design-vector reference is always the nom design, loaded explicitly when it is not in the evaluated list, and the vectors were verified to match a nominal-first list (S87). Held-out evaluation files are re-written with the corrected vector and carry the design list in their name (_des-s1.5-tau3).

Lesson 6
Mechanism modelling

Mechanisms need a loaded reference pose

Ball arrestors placed at the unloaded reset pose wedged the ball at the first step; they must be placed at the pose the robot settles into under gravity.

What happened

The model's reset pose starts the wheels 10 mm inside the ball; the loaded seat, where the robot actually rests, is about 1 cm higher with 2.2 mm of wheel penetration (S79). Arrestors that just touch the ball at the reset pose therefore press into it once the robot is seated, and the first attempt wedged the ball.

Two more pitfalls appeared while fixing it: the settle must start with the ball resting on the floor (dropping the robot wedged the wheels into the ball), and it must run on a flat copy of the model, because the first design's live model already carries the tile terrain (S79).

What it cost

Nothing was retracted: all three pitfalls were found and fixed before any arrestor result was kept, and arrestor runs start from the seated pose. The cost was time, and the lesson is recorded because the same mistake would silently change the outcome of the single most important mechanical result in the study (goal success 0.57 to 0.75 zero-shot, S79).

The rule and the guard

Rule. Place any mechanism that touches a loaded contact at the loaded pose: settle the model under gravity first, on the surface it will stand on, and derive the geometry from that pose.

Guard. experiments/warp_ppo/retainer.py: settle() lets the base settle onto the ball with the body held upright, on a flat copy of the model when the live one carries terrain, and the arrestor placement functions compute the loaded seat from that settled pose with zero preload (the docstrings state the rule).

Lesson 7
Perception and planning

Aim the sensor where the planner is going

Making the robot's motion smooth made its forward sensor miss obstacles, because a slowly turning command also turned the sensor slowly; the fix was to let the planner aim the sensor at its own target.

What happened

The first wavefront planner picked the best of 24 neighbours every step and jumped its heading (heading-rate RMS 14 rad/s). A smooth follower cut that to 1.7 rad/s with the perfect map at a cost of a few points (0.91 to 0.86 reached, S90).

With the real ToF sensor the smooth follower dropped from 0.85 to 0.72 reached, with 0.16 of worlds rolling onto a block. The head gimbal yawed to the command direction, and a rate-limited command sweeps the field of view slowly, so blocks to the side entered the map late (S90).

What it cost

Three fixes were tried and rejected: a proximity slow-down near seen obstacles (0.44 or 0.26 reached, because every route passes within 0.5 m of a block and the robot crawled), faster turning at 4 rad/s (0.74) and replanning every 0.04 s (0.69, the noisy map flickered). Aiming the sensor at the planner's target heading gave 0.78 reached and 0.03 on a block at the same smoothness (S90). About 7 points remain against the jerky planner, mostly slow or stuck approaches at the 20 s limit.

The rule and the guard

Rule. Smooth motion with a real sensor needs the sensor aimed where the planner is going, not where the robot is going; the navigation layer owns the sensor's aim.

Guard. experiments/warp_ppo/eval_nav.py sets env.yaw_override to the follower's target heading every step, and experiments/warp_ppo/train_dev.py honours that hook when computing the head yaw. On hardware this is the gimbal command from the navigation layer (Rule 8).

Lesson 8
Physics engine

A standing "fall" that was a solver blow-up

Three log entries treated a 20 s standing fall rate as a controller weakness, and one training run was designed to fix it, before the "falls" turned out to be the float32 contact solver going non-finite on a 1000 to 1 anisotropic friction ratio.

What happened

The wheel-ball contact pairs use anisotropic friction "0.001 1.0" with an elliptic cone: free rolling along the roller axis, grip across it. In MuJoCo-Warp float32 that ratio makes the Newton solve go non-finite when the robot stands still, preferentially on designs with a heavy ball relative to the body: in a 10 s LQR-alone test over 880 worlds, kb4 69 percent, bal025 28 percent, zeta66 25 percent, nominal 0 (S98).

The training termination counts a non-finite state as a fall, so these entered every 20 s standing number. The 8 s battery and the driving tests never showed it, because the blow-up needs a near-stationary wheel-ball contact.

The honest timeline: S93 read the standing falls as an LQR gain problem and concluded that the integral term was essential and that two ball-mass designs were unfixable; S94 measured the seed spread and a 20 s-episode run against it; S96 and S97 compared recipes and trained a standing-focused run (g25) to cure it. S98 then classified the "falls": on the worst seed, 91 percent were neither a tip nor an unseating but robots upright at 1 to 2 degrees of tilt whose state became NaN in one 10 ms step.

What it cost

Every 20 s standing fall rate in S93, S94, S96 and S97 (0.06 to 0.49 across seeds of the recommended controller) is void as a controller result, and the standing-focused recipe comparison is withdrawn: g25 answered an artefact. The design-level claims built on them (heavy-ball designs fail, integral term essential) must be re-measured. Driving numbers were affected only slightly (S98 addendum).

Finding it took ruling out, one at a time, the contact buffer size, the arrestors, the contact-frame kernel, warm start, the solver type, the iteration counts, domain randomisation and the height field, before the friction ratio: free-rolling 0.001 gives 12.7 percent non-finite worlds, 0.002 gives 0.1 percent, 0.005 and above give 0, with the real fall count unchanged at 64 to 69 of 880 (S98 addendum).

With free-rolling friction 0.01 the recommended policy, trained at 0.001, stands 20 s at 0.027 and 0.039 for seeds 1 and 2 (kb4 and bal025 at 0.00) and drives at 0.063 and 0.075. What remains is real: the light ball kb025 unseats within a second, and the heavy base bal4 falls in 0.18 to 0.23 of driving worlds.

The second consequence: the artefact had also hidden a real effect. A robot creeping toward an obstacle at 0.1 m/s is nearly stationary for most of the episode, the blow-up condition, so the S87 speed sweep was inflated most at low speed (all-tile falls 0.42 at 0.1 m/s against 0.28 on the corrected model) and read as "speed does not matter". On the corrected model falls rise steadily with commanded speed, 0.28 / 0.34 / 0.35 / 0.40 / 0.51 at 0.1 / 0.2 / 0.3 / 0.6 / 0.9 m/s (S100), and obstacle size still dominates (S88 re-check unchanged within 0.11). So the blow-up had hidden a real but small speed dependence. The speed layer's apparent large gain when it was re-tested (a halving in 15 s episodes) did not come from the blow-up but from exposure: with 40 s episodes it is worth 0.03 to 0.05 of obstacle falls (S103, lesson 3).

The same artefact bit a second time. After the fix, the training script and the battery script read the run's own free-rolling friction from its args.json, but one evaluation script (eval_governor.py) and five others did not, so policies retrained at 0.01 were evaluated on the obstacle course at the old 0.001. That produced an apparent gap, the retrained seeds gaining less from slowing down (0.32 to 0.35 with the speed layer against 0.18 to 0.19 for the older seeds), a hypothesis to explain it, and a three-seed training run to test the hypothesis. Evaluated on the same contact model the two are equal within 0.02: 0.16 against 0.17 with the speed layer, 0.37 against 0.35 without. The gap, the hypothesis and its test run were withdrawn (S102). (These are 15 s obstacle-course runs, valid as 15 s measurements only; the speed-layer gain they show was later withdrawn as an exposure artefact, S103, but the equality of the two checkpoint sets, measured on the same protocol on both sides, stands.)

The rule and the guard

Rule. In a float32 contact solver an extreme anisotropic friction ratio is a numerical hazard; a non-finite state must be logged separately from a physical fall; and a long stationary test belongs in every protocol, because a blow-up that needs a still contact is invisible to short or moving tests. When such an artefact is found, re-run the null results it touched as well as the positive ones: an artefact can hide a real effect as easily as it can invent one. When a model parameter changes, every evaluation and rendering path must read the run's parameters from one place, and a new result that contradicts the standard battery should first be checked for a configuration mismatch.

Guard. Free-rolling friction 0.01 is the model default (experiments/warp_ppo/train_dev.py --pair-mu1, recorded in args.json and re-applied by the evaluation scripts; the knob lives in common.load_cpu_model so it survives per-design and per-world friction batching). experiments/warp_ppo/fall_cause.py --stand classifies standing falls into tip, unseating and non-finite, and experiments/warp_ppo/nan_hunt.py is the stability test over 880 worlds. Since S102 all six evaluation and rendering scripts (eval_governor.py, fall_cause.py, render_policy.py, eval_nav.py, render_nav.py, nan_hunt.py) re-apply the free-rolling friction from the run's args.json when it is not set explicitly, and eval_governor.py records it in its output. The recommended checkpoints are the g26 seeds, retrained at 0.01.

A pattern. Five of the eight (lessons 1, 3, 4, 5 and 8) are measurement faults that produced a clean, plausible result pointing the wrong way, and each was caught by a check the result itself did not suggest: a cross-check against the model, a longer episode, a position record, a vector printout, a per-fall classification. The rules on this page are those checks, written down so they run before the next result, not after.
