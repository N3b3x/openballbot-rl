Live, in your browser

Drive the trained policy

A trained neural network balances the robot in your browser. It reads the robot's state 100 times a second and sets three wheel torques. MuJoCo, compiled to WebAssembly, runs the physics. Set a velocity, shove the robot, watch it recover. Simulation only.

Which policy this is. robs_c_s0: an early pure-PPO policy from the CPU study (study log, stage S13), with no LQR base. It is not the recommended controller g39_goalcentre_s0, which is not yet exported to the browser.

What the network does

Eight signals in, three torques out

A small network: 22 inputs (the eight signals below), two layers of 256 tanh units, 3 outputs. No camera. No memory beyond the last action and one integral term.

About 72,000 actor weights; 144,391 parameters including the value network used only in training.

What it sees (live)

The five rows marked standardised are shifted and scaled with the running mean and variance recorded during training, then clipped to ±10; cmd, heading and vint are fed raw. Together they make 22 numbers.

What it outputs (live)

Each output in [−1, 1] is multiplied by 30 and applied as the torque in N m on one omniwheel motor (with the sign convention of the model). Five physics steps of 2 ms are simulated per decision, so the policy acts at 100 Hz.

A known quirk. The input called motor_state is not the wheel speeds. The environment code (ballbot_gym/envs/ballbot_env.py) indexes the velocity vector by joint number, so the policy receives [base vy, base vz, base roll rate] / 30. It was trained on that signal, so this page reproduces it.

Why this was not obvious

Reproducing the omniwheel contact fix in JavaScript

Each omniwheel is a capsule that rolls freely along its axis (friction 0.001) and grips across it (friction 1.0). Stock MuJoCo picks the contact tangent arbitrarily, so the free direction can point the wrong way. The study's stepper rewrites every ball-wheel contact frame. The browser has to do the same.

How the browser does the same

  1. The official @mujoco/mujoco 3.13.0 build exposes the individual pipeline stages, so the step is split as in Python: kinematics, collision, rewrite frames, constraints, forces, then mj_implicit.
  2. data.contact is returned by copy, so writing to it has no effect. The frames are instead rewritten in place inside the live WebAssembly memory (data.arena), whose struct layout the page calibrates and verifies against data.contact before using it.
  3. Switch the fix off with the checkbox above and the robot falls almost at once, as in Python without the fix (control step 25 in the reference run).

Limits of this approach

  • It relies on the arena layout of MuJoCo 3.13.0, hence the pinned version and the start-up self-check. A different build could change the layout; the badge at the top turns amber if the check fails.
  • Single-threaded WebAssembly in your browser tab; speed depends on your device.
  • The model file is a snapshot of ballbot_gym/models/ballbot.xml with a down-scaled ball texture (visual only).
